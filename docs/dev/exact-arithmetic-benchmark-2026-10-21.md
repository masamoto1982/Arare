# 厳密算術の速度比較（2026-10-21）

Status: non-canonical. 観察ノート。ある日の一台の機械での測定値で、何も約束しない。
手順は `scripts/bench/exact-bench.mjs`（ケースは `exact-bench-cases.json`）にあり、
誰でも同じ表を作り直せる。

## 何を比べたか

同じ厳密な値を、六つの系がそれぞれ自分の型で計算する。比べたのは Ajisai（ネイティブの
リリースビルドと、同じエンジンを WebAssembly にしたもの）、FLINT 3.0.1（C、`-O2`）、
python-flint 0.9.0、SymPy 1.14.0（地の型は python-flint）、Python 3.13 の
`fractions.Fraction` である。畳み込みはどれも左から順に行う。ランナーは各系の答えを
Ajisai の表示（`p/q`、`[ a b ]`、`1/1+sqrt(2)`）で突き合わせ、答えが違う系には時間を出さない。
FLINT の Calcium（`ca`）は平方根の和を正規形で出せないので、そのケースは小数部の先頭
25 桁で照合した。WebAssembly 版の答えはネイティブ版の答えと DIGEST（値の内容の同一性）で
照合した。10 万要素のベクトルのように表示しきれない値も、エージェント用の上限を超える
計算も、値まるごと比べられる。今回は全ケースで全系の答えが一致した。

時間は 5 回の最良値。どの系も起動は測らない。Ajisai の時間には、ソースの解釈と、被演算子を
作る `RANGE` も含む。FLINT（C）の時間はループだけである。WebAssembly 版は Node 22 の上で、
`scripts/rebuild-wasm.sh` が作るバンドル（Playground のデプロイと同じ手順。固定版の
`wasm-opt` で最適化し、最適化の前後で 13,946 個のプログラムの答えが一致することを
確かめたもの）を測った。

## 結果

表は一度の実行で全系を測ったもの（加算を二度目に作り直し、作業メーターの値付けを分けた後）。

| ケース | n | Ajisai | Ajisai (WASM) | FLINT (C) | python-flint | SymPy | Fraction |
|---|---:|---:|---:|---:|---:|---:|---:|
| harmonic（Σ1/k） | 2000 | 1.13 ms | 2.49 ms | 0.58 ms | 1.41 ms | 32.0 ms | 3.69 ms |
| basel（Σ1/k²） | 2000 | 1.70 ms | 3.66 ms | 1.00 ms | 2.38 ms | 61.5 ms | 5.65 ms |
| newton-sqrt2（16 段、約 2.5 万桁） | 16 | 2.88 ms | 11.6 ms | 1.61 ms | 2.04 ms | 1.99 ms | 4.80 ms |
| elementwise（(k+1)/k · k/(k+2) のベクトル） | 100000 | 7.52 ms | 14.4 ms | 8.84 ms | 44.1 ms | 774 ms | 130 ms |
| sqrt-sum（Σ√k） | 100 | 0.39 ms | 1.06 ms | 1605 ms | — | 28.6 ms | — |
| sqrt-sum（Σ√k） | 1000 | 29.1 ms | 50.4 ms | 120 s で終わらず | — | 1039 ms | — |

「—」はその系に厳密な平方根がないこと（python-flint 0.9 は Calcium を出していない）。
この実行は同じ日の先の二回より機械全体が 3 割ほど速く、どの系も速めに出ている。比べるのは
同じ行の中の比である。FLINT（C）の newton-sqrt2 は実行ごとに 1.6〜3.2 ms の間で揺れた（大きな
数のメモリを毎回新しいプロセスで確保するため）。ほかの行の揺れは数 % だった。

## 読み取れること

- **有理数の畳み込み**は FLINT（C）が 1.7〜2.0 倍速い。Ajisai は、Python から FLINT を呼ぶ
  python-flint より速く、`Fraction` の約 3.3 倍、SymPy の 28〜36 倍速い。
- **桁の大きい多倍長**（newton-sqrt2）は FLINT・python-flint・SymPy が速い（1.4〜1.8 倍）。
  GMP の乗算と `num-bigint` の差である。ここは Ajisai が負けている。
- **ベクトルの要素ごとの演算**は Ajisai が FLINT（C）より速い（この実行で 1.2 倍、先の実行で
  1.5 倍）。小さい有理数の列を密な列のまま計算する経路（column kernels）が効いている。FLINT は
  要素ごとに `fmpq` を確保して掛ける。
- **平方根の和**は Ajisai の独壇場である。FLINT の `ca` は一般の代数的数を扱うので、
  √k を足すたびに体の拡大を組み直し、n = 100 で約 4000 倍遅く、n = 1000 は 2 分で
  終わらなかった。SymPy は n = 100 で 74 倍、n = 1000 で 36 倍遅い。Ajisai は平方根で
  生成される体（多二次体）の正規形を直接持つ（LANG.VALUES.EXACT）ので、その分だけ速い。
- **WebAssembly 版**はネイティブ版の 1.7〜4.0 倍の時間がかかる。差が大きいのは多倍長が
  重いケースで（newton-sqrt2 は 4.0 倍）、wasm32 では `num-bigint` の一桁が 64 ビットでなく
  32 ビットになり、同じ数を倍の桁数で掛けるためと見られる。差が小さいのはベクトルと平方根の
  和である。それでも WebAssembly 版は、有理数の畳み込みで `Fraction` より速く、SymPy の
  13〜17 倍速く、ベクトルの演算では FLINT（C）との差が 1.6 倍、平方根の和では FLINT より
  桁違いに、SymPy より 20〜27 倍速い。

訴求に使える主張は、「SymPy のように厳密で、有理数では python-flint 並み、ベクトルでは
FLINT（C）と同等以上、平方根を含む厳密計算では FLINT・SymPy のどちらよりも大幅に速い。
WebAssembly 版（Node の上で測った）でも、平方根の和では FLINT・SymPy より速い」までである。
「FLINT より速い」とだけ言えば、有理数の畳み込みと多倍長で事実と反する。

## 測定で見つけて直したこと

最初の測定で、Σ√k（n = 1000）に 1.9 秒かかった。原因は `Algebraic::add` が、足すたびに
両辺の基底をマージし、和の全項を新しい基底の上で分解し直していたことである（約 600 項、
約 170 個の基底要素で、一回の加算に 10 万回規模の多倍長の剰余）。直し方は二段になった。

1. 足す側の単項式がすでに和の基底の上で分解できるとき（√6 を {2, 3, 5, …} の和に足すとき）
   だけ近道した（`add_over_own_basis`。二段目で取り除いた）。1.9 秒が 316 ms になった。WebAssembly 版では
   2868 ms が 493 ms。
2. 近道をやめて、一般の加算そのものを、変わりうる部分だけ計算するように作り直した
   （`rust/src/types/exact/algebraic_sum.rs`）。基底のマージは、相手の要素と因数を共有する
   要素だけを細分化する（`Basis::merged`。乗算も同じマージを使う）。項は、マージで分割された
   要素を含むものだけを、分割された部分だけ分解し直す。打ち消し合いがなければ基底を刈り込まない。
   316 ms が 29 ms（WebAssembly 版は 50 ms）になった。答えが変わらないことは、作り直す前の
   加算を参照実装にした性質テスト（`algebraic_sum_tests.rs`）が確かめる。

二段目の途中で、作業メーターの穴も見つかった。足すたびに合成数の基底要素を一つ割る和
（`√(p₁p₂) + √(p₃p₄) + …` に `√p₁`、`√p₃`、… を足す）は、ネイティブで 51,880 単位/ms しか
課金されず、ほかの経路の 10 分の 1 だった。上限が時間の代わりにならない経路である。作り直しで
この形は 64 倍速くなり、ほかの和はさらに安くなったので、和の値付けを積と分けた
（`ALGEBRAIC_SUM_TERM_UNITS` = 256、積の `ALGEBRAIC_PAIR_UNITS` は 1,024 のまま）。最も高く
つく和でも、ネイティブで床の 1.8 倍、WebAssembly で床の 2.6 倍の単位/ms で課金される
（`examples/work_meter_calibration.rs`、`scripts/wasm-profile-calibration.mjs`）。MCP の
エージェント用上限の下で、`1 200 RANGE SQRT 0 [ ADD ] FOLD` は 10,097,345 単位で断られていたのが、
3,209,921 単位で答えるようになった。経緯は `mcp-host-profiles.md` にも書いた。

## 測っていないこと

- ブラウザの JavaScript エンジンの上での WebAssembly 版。上の数字は Node 22（V8）の上のもので、
  Chrome は同じ V8 なので近いと見込むが、Firefox・Safari では測っていない。
- 行列・多項式など、Ajisai の語彙にない計算。FLINT の本領はそちらにある。
