# Current GUI Design Memory

This note captures the current Ajisai web-playground GUI behavior for reference. The web deployment at https://masamoto1982.github.io/Ajisai/ is a playground; installable/desktop usage is provided via the Tauri wrapper (`src-tauri/`). The runtime boot is `src/entry/entry-common.ts` and platform-specific behaviors are abstracted in `src/platform/`. The web entrypoint is not a PWA and has no service worker.

## Overall structure
- Single-page web GUI (`index.html`) with a two-column main layout.
- Left/editor side can show **Input** or **Output**.
- Right/state side can show **Stack** or **Dictionary**.
- Mobile mode switches to a one-panel-at-a-time selector (`input/output/stack/dictionary`), cycled by the `Select panel` dropdown, by a horizontal swipe, or by a double-tap on the Stack or Output area.

## Header/footer and app chrome
- Header includes the Ajisai logo, the `Playground` badge, and links out to the MCP install instructions and the Reference. There is no Test button (the line that said so described a control that had been removed).
- Footer includes copyright + GitHub link.
- Skip link exists for accessibility (`Skip to main content`).

## Primary interaction model
- Main code entry is a textarea.
- Run via `Shift+Enter`, or a triple-tap (touch) in the editor. A desktop triple-click used to run too, and was removed: it is the line-select gesture of every text field, and a Run cannot be undone. There is deliberately no Run button: one was added and removed again — see "Touch interaction" below.
- Step execution via `Ctrl+Enter`.
- Abort via `Escape`. The window-level Escape listener captures and stops propagation, so it asks the editor first (`Editor.dismissSuggestions`): an open suggestion panel takes the key and closes, and Abort gets Escape only when there is no panel to close. Without that hand-off the panel could not be dismissed with Escape at all.
- Full reset via `Ctrl+Alt+Enter`, which asks first (`RESET_CONFIRM_MESSAGE`).
- **Recall of submitted source** via `Ctrl+Up` / `Ctrl+Down` (`createEditorHistory` in `src/gui/code-input-editor.ts`). A successful Run clears the editor and Reset clears it too, while the Stack persists across runs; without recall the natural edit-and-rerun loop meant retyping the whole program. History is session-lived, holds source text only, survives Reset, and stores neither values nor dictionary entries. The plain arrows are left to caret movement and to the suggestion panel's own list navigation.
- Output panel supports copy-to-clipboard.
- Double-clicking the Output area (desktop) switches the left column back to the editor and focuses it.

## Touch interaction (mobile presentation)
- **The editor gets the room; the placeholder does the teaching.** A touch action bar carrying Run, Step, Stop, Look up and Reset was added under the editor and then removed, because of what it cost: with the bar (96px) and an in-flow symbol palette (196px) below it, tapping into the editor collapsed it from 383px to **179px** on a 360x740 phone. The editor is what the page is for. Run stays on the triple-tap; Step, Abort, Lookup and Reset stay on their shortcuts and are reachable on a phone only from an attached keyboard. The mobile placeholder says all of this in 19 lines, which is free — the editor is empty whenever it shows. (The bar, the in-flow palette and a swipe exemption list came from a 2026-09 external mobile-usability report; all three were withdrawn after use on a real phone, and the report's validation memo was retired once the outcome was recorded here.)
- **Keep every placeholder line under 27 characters.** A textarea placeholder wraps on width, so a hand-aligned continuation line lands wherever the wrap leaves it; at 360px that turned a tidy two-column sheet into ragged prose. Short whole lines read the same from 320px up.
- **A tap is a stationary touch.** `createMultiTapRecognizer` and `checkIsStationary` (`src/gui/gui-layout-state.ts`) count a run of taps only while they stay inside the interval *and* inside the movement tolerance of the run's first tap. The tap counting used to sit inline in the bindings and read every `touchend` as a tap, so the end of a drag-to-select, and each release of a pinch, counted toward the triple-tap that runs the program.
- **The panel-cycling swipe has no exemption list, on purpose.** One was tried (`checkIsSwipeExempt`), withholding a horizontal drag that began on a textarea or input on the reasoning that it was a text selection. On a touch screen it is not — selecting text there is a long-press and then the selection handles. What it actually did was kill the swipe across most of the Input surface, so the gesture that reaches all four surfaces stopped working on the one the app opens on; only the footer, outside the list, still answered. The handler still drops a gesture that grew a second touch (a pinch).
- **Symbols come from the phone's own keyboard.** The Playground has no symbol input aid. Three forms were tried on a phone, and each failed on the screen it has to share with the OS keyboard. A 30-symbol pad at the caret covered the text being written, and it could not reliably get out of the keyboard's way, even when placed above the caret line using `visualViewport`. The pad pinned to the editor's bottom edge, and a paged row of keys under the editor, both sat exactly where the keyboard rises. Ajisai source needs few symbols (`[ ]`, the quote, the characters of a number), and every phone keyboard has them one layer away. The suggestion panel completes Words only, on both presentations. A completion never takes focus (`pointerdown` is swallowed), so the keyboard stays up.
- **Two spacings, and only two.** 0.75rem holds a content box's contents off its frame and the page off its edges — `#code-input`, `#output-display`, `#stack-display` and `.words-display` all pad by it. 0.5rem separates two things stacked inside a surface. A value belonging to neither is a bug: `.words-display` padded by 4px and sat its chips 6px from a frame every box beside it held at 13px. The word chips keep their own 1px margins inside that — spacing between chips is a denser thing than the frame around all of them, and is meant to look it.
- **One gap, 0.5rem, between anything stacked inside a surface — including the seam under the panel selector.** That seam used to be 0.75rem on mobile and 0.5rem on desktop, for a reason that was never a decision: desktop keeps its selector *inside* the panel, where the panel's own `gap` separates it from the content, while mobile's `.area-selector-mobile` is a sibling *above* the panel, so the space below it was the panel's `padding-top`. The mobile panels take `padding: 0.5rem 0.75rem 0.75rem` — the other three sides stay at 0.75rem, being the page gutter rather than a gap between two stacked things. Visible at its worst in the Dictionary, where two selectors stack and the reader sees 12px then 8px one under the other.
- **A word's summary and example are its `title`.** They used to be written into a line of text above the list, by a `mouseenter`/`mouseleave` pair that filled it and cleared it again — a hover display built by hand. It cost a row of the surface whether or not anything was being hovered, and because its height changed with the text, the list under it re-flowed every time the pointer crossed a chip, enough that a real click could land on a word that had since moved. The browser's own tooltip is the same idea with none of that: it owns the timing, the placement and the dismissal, and the Dictionary gets 60-80px back (the list box goes 395px → 459px at 360x740). Core Words carry their text in the same payload as the name; a User Word's is read at render by `lookupUserWordTooltip`, because a tooltip has to hold its text before the pointer arrives.
- **A tooltip needs a pointer, and a phone has none.** This is the accepted cost of the line above: on touch there is no hover, so `title` shows nothing and the mobile Dictionary now lists what exists without explaining any of it. The Reference (header link) is where a phone reader goes for what a Word does.
- **The Dictionary is a catalogue first on a phone.** A word button types its name into the editor on both presentations (`onWordClick`, `gui-application.ts`; the mobile placeholder says `tap a Dictionary word too`). The mobile chip is still sized to show the vocabulary rather than to be a 44px target: the Core Words fit in a few rows inside the list box, with no scrolling, and a chip that inserts a name is pressed deliberately, not in a hurry. If that trade is revisited, the 44px floor below is where it goes. The text is *not* smaller than desktop (0.75rem either way) — what shrank is the padding and margin the 44px floor was inflating. Two rules have to be turned off for that: the mobile block restates `font-size`, `padding` and `margin` to opt out of the `@container panel (max-width: 26rem)` rule, which grows chips for a slim desktop column and cannot tell one from a phone. Below 340px the type does step down to 0.65rem, the one place where seeing all of it outranks a larger glyph. A 320x568 screen (2016-era 4in) still scrolls even with the hint row gone: 9 words past the edge of a 287px box.
- **Text fields are at least 16px, and tap targets 44px where the 44px is free** in the mobile block of `src/styles/playground.css`. Under 16px, iOS Safari zooms the page on focus and does not zoom back. The corner buttons are absolutely positioned, so their hit area grows at no cost to the layout. The header's links are the exception and stay at 34px: the header sits above all four surfaces, so a floor there is subtracted from all four.
- **A selector is one size, on every viewport.** The controls that switch what a surface shows are not among the 44px targets, and the reason is what happened when they were: the panel selector took the floor, the dictionary sheet selector (Core/User) had it taken back off to give the word list its 14px, and the same part — a dropdown that swaps a surface's contents — then stood 44px in one place and 30px in the other, the two of them one under the other in the mobile Dictionary. A floor that has to be granted to one member of a set and withheld from another is not a rule. Both now take the size the shared base rule gives every selector, which is also the desktop size, and the mobile word list keeps the 19px that comes back. The Core/User selector is a plain `<select>` (`#dictionary-sheet-select`) like the two area selectors; it was a custom popup over an inert native select, a shape left from when the dictionary had many sheets, and it had no arrow-key navigation. It shares the Dictionary area's own toolbar (`.dictionary-toolbar`) with the one word search (`#dictionary-search`): the search belongs to the area, so there is one of it whichever area selector — desktop's right column or mobile's single one — brought the Dictionary up. It used to sit beside each selector that could show the Dictionary, as two synchronised inputs. Mobile-only in the area-selector row is the page gutter and the surface colour it needs for standing outside the panel.

## Dictionary UX
- Dictionary panel shows one of two sheets, Core Words or User Words (the two tiers of LANG.DICTIONARY.RESOLUTION), chosen by the CU selector (`#dictionary-sheet-select`); a run that defines or deletes a User Word brings the User sheet up.
- A User Word button is coloured apart when another User Word calls it (`.dependency`): DEL and DEF refuse it until that caller is gone. Delete is on the button's context menu; a refusal is shown with the engine's message naming the callers.
- A failed run's dictionary changes are discarded with the run (the session keeps its pre-run dictionary), and the output names the `Defined word:` lines that did not hold.
- Search box with clear button filters dictionary words.
- User word sheet supports import/export actions.

## Data/state behavior
- Stack display and dictionary update after execution.
- **The Stack area's drawing is bounded** (the render budget in `src/gui/output-display-renderer.ts`): at most 100 elements are drawn from any one collection and at most 2000 across a whole render, with the undrawn tail replaced in place by a `… N more` marker (styled as muted italic commentary so it cannot be read as part of the value). The interpreter's materialization ceiling bounds what a generative Word may build, not what the host may draw: `[ 1 500000 ] RANGE` is a legal program well inside that ceiling, and drawing one DOM node per element locked the tab for ~27s with no way to abort, clear the editor, or read the result. The bound is presentation, in the same class as the step limit — the value on the stack is whole and every Word still sees all of it.
- Relatedly, `detectExecutionSurfaceChanges` compares the pre/post stack **structurally with an early exit** rather than by `JSON.stringify` of both: two full serializations of a possibly-huge stack ran on every single run to answer a question a first difference settles.
- The top of the stack — the value the next Word takes and consumes (LANG.STACK.CONSUMPTION) — is filled with a very pale warm red (`--color-stack-top` in `playground.css`) and set in bold. One CSS rule does it (`.stack-item:last-child .stack-node[data-depth="1"]` in `playground.css`); the renderer only tags top-level nodes, canonical and LaTeX alike, with `data-depth="1"`. A fill rather than a text colour, so the bracket depth-colours that show Vector nesting stay intact; no outline. This replaced a two-axis highlight driven by modifier tokens typed in the editor (`.`/`..` choosing the top or the whole stack, `,`/`,,` choosing an eat or keep tint): the language dropped those modifiers, and nothing of that scanning remains in the GUI.
- GUI tracks layout state (`currentMode`, `currentLeftMode`, `currentRightMode`).
- Desktop and mobile layouts sync via selectors and `body[data-active-area]`.

## Stack math view (KaTeX)
- The Stack area renders the canonical protocol strings **by default**; a checkbox labeled **LaTeX** (bottom-right of the Stack area, persisted in `localStorage`) opts into KaTeX-typeset mathematics: rationals as fractions, rank-1/rank-2 numeric vectors and tensors as matrices, `approximate` nodes with a leading approx sign. Keeping the math view opt-in keeps the GUI's standard surface independent of KaTeX (portability).
- The unchecked (standard) mode is deliberately **unnamed**: a checkbox only states what checking it adds, so no name for the default view is needed. Naming the default "Ajisai" was considered and rejected — it would be ambiguous with the language name.
- Fractions with a ten-or-more-digit numerator or denominator render at six significant digits — as a plain decimal for human-scale values (a best rational approximation of sqrt(2) shows as approx 1.41421, not as a ten-digit fraction) and as a power of ten outside 10^-4..10^5 — always with a leading approx sign unless the shortened form is exactly the value. The math node also scroll-contains itself so an oversized rendering never clips at the panel edge.
- **Presentation only.** The canonical display strings (`3/1`, bracketed vectors, an irrational's normal form such as `1/1+sqrt(2)`) remain the default rendering and the conformance observation; the math view never changes a value or its protocol string.
- **Structure-driven, never text-scanning.** LaTeX is derived from the structured `Value` protocol (`valueToLatex` in `src/gui/output-display-renderer.ts`, pure and unit-tested); `katex.renderToString` runs only on that generated TeX. The Output area is user text and is deliberately not math-rendered — auto-render-style delimiter scanning is never used in the GUI.
- Values without a faithful flat math reading (strings, NIL, booleans, ragged or rank>=3 data, oversized matrices, text-hinted byte tensors) return `null` and fall back to the canonical text node.
- An irrational is an algebraic value in multiquadratic normal form, and the protocol carries that form as `semantics.exactTerms`, so the math view typesets the exact value (`\sqrt{2}`, `1 + \sqrt{2}`) from those terms (`normalFormToLatex`). The engine has no continued-fraction value any more, so there is no nested `\cfrac` to draw.

## Technical composition
- GUI implemented as modular TS components under `src/gui/`.
- The entry module (`src/entry/entry-common.ts`) waits for the DOM through the platform's `runtime.onReady` and starts the splash, labels and WASM/GUI initialization; the web/Tauri difference lives in the `src/platform/` adapter it goes through, not in separate entry files.
- Worker manager used for parallel execution and abort handling.
- Persistence/file I/O go through `src/platform/` adapters:
  - Web: IndexedDB + browser file APIs (`src/platform/web.ts`)
  - Tauri: app-data JSON persistence + native dialogs/fs (`src/platform/tauri.ts`); the adapter interfaces and runtime detection are in `src/platform/index.ts`
- No service worker / offline-mode integration in the web app entrypoint.
- GUI behaviour is tested with vitest (`src/gui/*.test.ts`) against fake interpreters, and by Playwright runs against the dev server during review; there is no in-app test runner.

## Styling profile
- Styling lives in `src/styles/playground.css`, one file in three sections: tokens (colours, spacing, type), base (elements and the shared button), components (each surface).
- Layout relies on flex containers with explicit panel visibility toggles.
